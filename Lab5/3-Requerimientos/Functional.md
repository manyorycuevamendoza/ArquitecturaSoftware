# Requerimientos funcionales

El enunciado interpretado, los SPOF y los puntos de decisión están en
[../1-Problema/Problema.md](../1-Problema/Problema.md). Las personas que dan
origen a cada necesidad están en [../2-Personas/](../2-Personas/README.md).

Cada requisito se traza a un **componente del diagrama**
([../Diagrams/diagramaLab5.excalidraw](../Diagrams/diagramaLab5.excalidraw))
y al **punto de decisión (PD)** que lo resuelve. Los requisitos no tienen
responsable individual: nacen del problema, no de una persona.

## Problema 1: el LLM ejecutó una acción destructiva

| ID        | Requerimiento                                                                                                          | Criterio de aceptación                                                                                                                                         | Componente del diagrama                              | PD    |
| --------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ----- |
| FR-ACT-01 | Toda herramienta que el LLM puede usar está en un catálogo con clase de riesgo: solo lectura, escritura o destructiva. | Una herramienta fuera del catálogo no se ejecuta aunque el modelo la nombre; el intento se rechaza y se registra.                                              | Orquestador de herramientas                          | PD-2  |
| FR-ACT-02 | El LLM **propone** acciones; el Orquestador las valida y ejecuta.                                                      | Ninguna llamada llega a un sistema sin pasar por el Orquestador. Propuesta y decisión quedan como dos registros separados en Auditoría.                        | Orquestador de herramientas, Auditoría               | PD-1  |
| FR-ACT-03 | Toda consulta de escritura genera una vista previa de impacto antes de ejecutarse.                                     | La vista previa muestra sistema, operación y cantidad de registros afectados. Sin vista previa no se habilita la aprobación.                                   | Vista previa de impacto                              | PD-3  |
| FR-ACT-04 | Una acción que cambia o borra datos queda bloqueada hasta que el Incident Manager la aprueba.                          | El aprobador es distinto del solicitante, ve la misma vista previa y su decisión caduca en el plazo de `NFR-SEC-03`. El LLM no puede aprobar.                  | Bloqueo de escritura, Aprobación de la acción        | PD-3  |
| FR-ACT-05 | Las acciones se ejecutan con los permisos del ingeniero que las pide, no con una credencial del harness.               | El rol por defecto es solo lectura. Un ingeniero sin permiso sobre un sistema recibe un rechazo, no una ejecución parcial.                                     | Auth y rol, Permisos del ingeniero                   | PD-4  |
| FR-ACT-06 | Toda acción destructiva se puede deshacer.                                                                             | Un borrado de incidencia es lógico: se revierte con "Deshacer acción" dentro del tiempo de `NFR-REC-01` y la incidencia borrada deja de aparecer como similar. | Borrado de incidencia, Deshacer acción               | PD-3  |
| FR-ACT-07 | El texto del incidente y del cliente es dato, nunca es una instrucción.                                                | Un incidente cuyo cuerpo pide "borrar la base de datos" no produce ninguna acción; el intento queda registrado como evento de seguridad.                       | Pregunta en lenguaje natural, System prompts         | PD-5  |
| FR-ACT-08 | Las pruebas E2E corren solo contra el entorno de pruebas con réplica anonimizada, nunca contra producción.             | Producción no está en el alcance de la herramienta E2E; un intento contra producción se rechaza con motivo.                                                    | Pruebas E2E, Entorno de pruebas, Réplica anonimizada | PD-2  |
| FR-ACT-09 | El Incident Manager puede cortar todas las acciones con un kill switch sin apagar las consultas.                       | Activado el corte, toda acción pendiente se rechaza y las consultas de estado siguen respondiendo. El corte y su reversión quedan registrados.                 | Kill switch de acciones                              | PD-1  |
| FR-ACT-10 | Cada acción tiene un identificador único y es idempotente ante reintentos.                                             | Repetir una ejecución con el mismo `actionId` devuelve el resultado anterior sin volver a ejecutar ni cerrar dos veces la incidencia.                          | Ejecución, Cierre de incidencia                      | PD-1  |
| FR-ACT-11 | Cada usuario ve y opera solo lo que su rol permite.                                                                    | El cliente accede solo a sus incidencias; el Incident Manager aprueba pero no ejecuta; los ingenieros operan según su área.                                    | Auth y rol                                           | PD-4  |
| FR-ACT-12 | Toda propuesta, aprobación, rechazo y ejecución queda en una auditoría que el harness no puede alterar.                | Cada registro guarda solicitante, incidente, vista previa, aprobador, resultado y hora. El día del borrado se puede reconstruir solo con la auditoría.         | Auditoría                                            | PD-15 |

## Problema 2: respuestas erróneas, distintas cada vez y desactualizadas

| ID        | Requerimiento                                                                                         | Criterio de aceptación                                                                                                                      | Componente del diagrama                                                                          | PD         |
| --------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------- |
| FR-ANS-01 | Cada pregunta se clasifica en estado, pregunta frecuente, analítica o acción antes de invocar al LLM. | Las consultas de estado y las frecuentes con respuesta en caché se responden sin usar el modelo; el registro muestra cero generaciones.     | Pregunta en lenguaje natural                                                                     | PD-9       |
| FR-ANS-02 | El estado de una incidencia se lee de BD1, nunca del histórico ni de una caché vencida.               | Cerrar una incidencia y preguntar por ella devuelve "cerrada" dentro de la ventana de `NFR-FRE-01`.                                         | Estado de incidencia, BD1                                                                        | PD-6       |
| FR-ANS-03 | Toda respuesta entrega la hora del dato y la fuente que la sustenta.                                  | La respuesta incluye identificador de incidencia y hora de lectura. Una respuesta sin hora del dato no se entrega.                          | Respuesta con hora del dato                                                                      | PD-6       |
| FR-ANS-04 | Las preguntas frecuentes tienen respuesta en caché que se invalida cuando cambia el dato.             | La misma pregunta frecuente devuelve la misma respuesta literal; si cambia el dato que la sustenta, la caché se regenera.                   | Caché de preguntas frecuentes                                                                    | PD-7, PD-9 |
| FR-ANS-05 | Sin dato que sustente la respuesta, el sistema se abstiene y deriva.                                  | Ante una incidencia inexistente el sistema no afirma nada: responde "sin dato" e indica a quién acudir.                                     | Abstención                                                                                       | PD-8       |
| FR-ANS-06 | Varias respuestas candidatas del LLM se reducen a una sola por match determinístico.                  | Veinte ejecuciones de la misma pregunta devuelven la misma respuesta mientras el dato no cambie.                                            | Match determinístico                                                                             | PD-9       |
| FR-ANS-07 | Cada generación registra modelo, prompt, temperatura y semilla.                                       | La temperatura del camino factual es cero. Un cambio de versión de modelo o prompt queda fechado y pasa antes por el eval set.              | System prompts, LLM                                                                              | PD-9       |
| FR-ANS-08 | Las incidencias similares se recuperan del histórico BD2 como contexto para el LLM.                   | La respuesta cita las incidencias similares usadas; la consulta a BD2 es de solo lectura; una incidencia borrada no aparece como similar.   | Incidencias similares, Consulta de solo lectura, BD2                                             | PD-8       |
| FR-ANS-09 | Una incidencia escalada se abre con su contexto ya cargado.                                           | El ingeniero de desarrollo recibe la incidencia con estado, similares y datos del cliente sin tener que preguntarlos.                       | Incidencia escalada                                                                              | PD-8       |
| FR-ANS-10 | El ingeniero puede calificar una respuesta con score y motivo.                                        | La calificación se guarda en BD3 junto con la respuesta y el dato usado. Una respuesta en caché con dos calificaciones negativas se retira. | Score y motivo de la respuesta, BD3                                                              | PD-10      |
| FR-ANS-11 | El conocimiento se cura antes de llegar al LLM: de dato crudo a conocimiento validado.                | Nada de BD3 entra al modelo sin pasar por Curación. El conocimiento validado tiene autor, fecha y vigencia.                                 | Ingesta de data del cliente, Curación de conocimiento                                            | PD-10      |
| FR-ANS-12 | Todo cambio al conocimiento del LLM pasa por el eval set y por aprobación del Incident Manager.       | Un cambio que empeora exactitud o abstención correcta en el eval set no se publica.                                                         | Enriquecimiento del LLM, Eval set de respuestas conocidas, Aprobación de cambios al conocimiento | PD-10      |
| FR-ANS-13 | Cada respuesta se escala por tipo de incidencia y notifica al ingeniero correspondiente.              | Una customer escalation notifica a soporte; una engineering escalation, a desarrollo. La notificación lleva el enlace a la incidencia.      | Escalamiento por tipo, Notificación al ingeniero                                                 | PD-11      |

## Problema 3: el pico de la primera semana y la tolerancia a fallos

| ID        | Requerimiento                                                                                                      | Criterio de aceptación                                                                                                                                                                   | Componente del diagrama                                             | PD    |
| --------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----- |
| FR-REL-01 | Cada solicitud recibe clase y prioridad en la entrada según el tipo de escalamiento.                               | La solicitud lleva `CUSTOMER`, `SUPPORT` o `ENGINEERING` y su SLA; la clase la define la incidencia, no quién pregunta.                                                                  | Auth y rol, Cola por prioridad                                      | PD-11 |
| FR-REL-02 | La cola atiende primero cliente y después ingeniería, con capacidad reservada por clase.                           | Con la cola de ingeniería saturada, una consulta de cliente se admite dentro de `NFR-PER-02`.                                                                                            | Cola por prioridad                                                  | PD-11 |
| FR-REL-03 | Toda llamada a una dependencia tiene tiempo de espera y reintento acotado.                                         | LLM, BD1, BD2 y Slack tienen tiempo de espera propio. Las escrituras no se reintentan solas; se devuelven al usuario.                                                                    | Orquestador de herramientas                                         | PD-12 |
| FR-REL-04 | Cada dependencia tiene un cortacircuito que desvía al modo degradado.                                              | Tras los fallos configurados, el circuito abre y las siguientes solicitudes no esperan el tiempo completo. Su estado se ve en el dashboard.                                              | Circuit Breaker, Modo degradado, Métricas y dashboard               | PD-12 |
| FR-REL-05 | Con el LLM caído o saturado, el sistema responde estado y preguntas frecuentes sin modelo.                         | Con la inferencia apagada, estado y caché siguen respondiendo y la respuesta indica que se generó sin modelo.                                                                            | Modo degradado, Estado de incidencia, Caché de preguntas frecuentes | PD-13 |
| FR-REL-06 | Bajo saturación se descarta por prioridad, con motivo.                                                             | Se rechazan primero las solicitudes de ingeniería de baja criticidad, con posición y tiempo estimado. Ninguna customer escalation crítica se descarta mientras haya capacidad reservada. | Cola por prioridad                                                  | PD-13 |
| FR-REL-07 | Ningún componente del camino de consulta es único: LLM, orquestador y servicios de entrada tienen redundancia N+1. | Apagar una réplica durante la prueba de carga no produce errores visibles.                                                                                                               | LLM N+1, Orquestador de herramientas N+1, Cola por prioridad N+1   | PD-14 |
| FR-REL-08 | BD1 y BD2 tienen réplica y relevo automático.                                                                      | El relevo cumple `NFR-REC-02`. Durante el relevo el estado se sirve desde la réplica marcando el retraso y no se aceptan escrituras.                                                     | BD1 (réplica + failover), BD2 (réplica + failover)                | PD-14 |
| FR-REL-09 | Cada componente expone verificación de salud y sale del balanceo si no está sano.                                  | Una réplica de LLM con la cola llena se declara "no lista" y deja de recibir tráfico sin reiniciarse.                                                                                    | Todos los servicios del harness                                     | PD-14 |
| FR-REL-10 | Slack y las notificaciones no bloquean: su caída no impide aprobar ni responder.                                   | Con Slack caído, la aprobación sigue disponible dentro de Genius; al volver, cada notificación pendiente se entrega una sola vez.                                                        | Notificación al ingeniero, Aprobación de la acción                  | PD-12 |
| FR-REL-11 | El Incident Manager ve métricas por clase y recibe alertas antes de que la degradación sea visible.                | El dashboard muestra latencia, cola, saturación del LLM y estado de cortacircuitos; alerta al 80% de cualquier umbral.                                                                   | Circuit Breaker, Métricas y dashboard                              | PD-12 |
| FR-REL-12 | La tolerancia a fallos se prueba apagando componentes a propósito.                                                 | Cada periodo se apagan LLM, BD2, cola y Slack en simulacro; se compara lo esperado con lo observado.                                                                                     | Todos los servicios del harness                                     | PD-14 |

## Cobertura de los pain points del caso

| Pain point del enunciado                                                | Requisitos que responden                                          |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------- |
| El LLM borró la base de datos por una instrucción de soporte.           | `FR-ACT-02`, `FR-ACT-03`, `FR-ACT-04`, `FR-ACT-05`, `FR-ACT-06`   |
| El texto de un incidente puede convertirse en una orden.                | `FR-ACT-07`, `NFR-SEC-01`                                         |
| Genius responde el estado de una incidencia cerrada hace horas.         | `FR-ANS-02`, `FR-ANS-03`, `FR-ANS-04`, `NFR-FRE-01`               |
| La misma pregunta recibe respuestas distintas cada día.                 | `FR-ANS-04`, `FR-ANS-06`, `FR-ANS-07`, `NFR-DET-01`               |
| El LLM no aprende y repite errores.                                     | `FR-ANS-10`, `FR-ANS-11`, `FR-ANS-12`, `NFR-DET-02`               |
| La primera semana del mes el LLM no responde o responde mal.            | `FR-REL-02`, `FR-REL-05`, `FR-REL-06`, `NFR-AVL-02`, `NFR-CAP-02` |
| Cualquier componente caído tumba todo el sistema.                       | `FR-REL-04`, `FR-REL-07`, `FR-REL-08`, `NFR-AVL-03`               |
| Una consulta rutinaria de ingeniería retrasa una escalación de cliente. | `FR-REL-01`, `FR-REL-02`, `NFR-PER-02`                            |
